# PHP2Shell: Two Critical PHP Vulnerabilities Could Let Attackers Take Control of Web Servers

**Published:** November 3, 2026\
**Category:** Web Application Security\
**Reading time:** 8–10 minutes

## Introduction: Is Your PHP Application Really Secure?

PHP powers a significant portion of the web. From business websites and e-commerce platforms to content management systems and custom SaaS applications, it remains a critical part of modern web infrastructure.

But what happens when the vulnerability is not in your application's business logic, database queries or authentication system, but in the PHP runtime itself?

On October 21, 2026, the PHP development team released emergency security updates addressing two critical vulnerabilities:

* **CVE-2026-109618:** Remote code execution through out-of-memory corruption.
* **CVE-2026-109619:** Remote code execution through stale global state.

Together, these vulnerabilities have become known as **PHP2Shell**.

Both vulnerabilities carry a CVSS v4.0 score of 9.2 out of 10 and could allow unauthenticated attackers to execute malicious code on vulnerable PHP servers under affected conditions.

This is not just another application-level security issue. It affects the underlying runtime responsible for processing web requests.

For businesses running PHP applications, the question is no longer whether their application has secure authentication or input validation. It is whether the infrastructure running that application is secure in the first place.

## 1. What Is PHP2Shell?

PHP2Shell refers to two critical vulnerabilities discovered in the PHP runtime.

Unlike conventional web application vulnerabilities, which might require an attacker to exploit a particular endpoint or application feature, these vulnerabilities involve how PHP handles internal memory and request-related state.

The security implications are significant because PHP processes incoming web requests through its runtime before application-level code executes.

An attacker who can trigger the vulnerable conditions may be able to achieve remote code execution without authenticating to the application.

In practical terms, successful exploitation could allow an attacker to execute commands on the server, access sensitive information, interfere with application operations or establish further access, depending on the environment and privileges of the PHP process.

The PHP security team released fixes across supported PHP branches on October 21, 2026.

## 2. Understanding the Two Critical Vulnerabilities

### CVE-2026-109618: Remote Code Execution Through Out-of-Memory Corruption

**Severity:** Critical\
**CVSS v4.0:** 9.2\
**Impact:** Potential unauthenticated remote code execution

PHP uses memory allocation and internal error-handling mechanisms to process incoming requests.

When PHP encounters an out-of-memory (OOM) condition, it uses internal control-flow mechanisms to interrupt the current execution context and abort request processing.

The vulnerability occurs when certain internal request structures have not been completely initialized before this interruption takes place.

During subsequent request cleanup, PHP may incorrectly treat partially initialized memory as valid data.

This creates an opportunity for memory corruption.

Under certain conditions, an attacker can trigger the vulnerable allocation and cleanup behaviour through specially constructed requests. Researchers have demonstrated that this condition can be exploited to achieve remote code execution.

**Why this matters**

Imagine a web server processing thousands of requests every minute.

An attacker does not necessarily need to find an SQL injection vulnerability, bypass authentication or compromise an administrator account.

If the PHP runtime itself can be forced into a vulnerable memory-handling state, the attack surface exists below the application's normal security controls.

That makes this issue particularly concerning for publicly accessible PHP services.

### CVE-2026-109619: Remote Code Execution Through Stale Global State

**Severity:** Critical\
**CVSS v4.0:** 9.2\
**Impact:** Potential unauthenticated remote code execution

The second vulnerability involves how PHP manages global state associated with individual requests.

During request processing, certain internal global variables temporarily reference memory owned by that request.

When the request finishes or encounters certain fatal errors, the memory may be released.

However, under specific conditions, PHP may fail to correctly reset or reinitialize these references.

As a result, internal state can continue pointing to memory that has already been freed.

This is commonly described as a use-after-free or stale-reference condition.

A later request handled by the same worker may interact with this stale state before it has been properly initialized.

With carefully constructed conditions, attackers can potentially manipulate this behaviour to achieve remote code execution.

**Why this matters**

PHP applications frequently use persistent worker processes.

A worker may handle multiple requests during its lifetime.

If request-specific state is not correctly cleaned up, the effects of one request can potentially influence the processing of another.

This is a serious memory-safety concern because the vulnerability exists within the runtime's internal request lifecycle.

## 3. Which PHP Deployments Are Affected?

The vulnerabilities affect PHP installations serving web requests, including:

* PHP-FPM
* Apache with mod\_php
* PHP-CGI
* FrankenPHP
* LiteSpeed

The PHP development team considers Apache deployments using mod\_php particularly high-risk because a demonstrated exploit can trigger the issue before application code runs.

### Affected and Fixed Versions

| PHP Branch        | Vulnerable Versions | Fixed Version             |
| ----------------- | ------------------- | ------------------------- |
| PHP 8.5           | Before 8.5.12       | 8.5.12                    |
| PHP 8.4           | Before 8.4.27       | 8.4.27                    |
| PHP 8.3           | Before 8.3.36       | 8.3.36                    |
| PHP 8.2           | Before 8.2.35       | 8.2.35                    |
| PHP 8.1 and older | Affected            | No supported security fix |

PHP 8.1 and older versions are end-of-life and no longer receive security updates from the PHP project.

Simply updating an application framework or installing the latest WordPress plugins does not necessarily resolve a vulnerability in the underlying PHP runtime.

The actual PHP installation and its deployment configuration must be checked.

## 4. Are Attackers Already Exploiting These Vulnerabilities?

This is where the situation becomes more concerning.

The two PHP2Shell vulnerabilities have been added to the US Cybersecurity and Infrastructure Security Agency's Known Exploited Vulnerabilities (KEV) catalog.

Security advisories have also reported successful exploit demonstrations against products integrating PHP, including WordPress, Drupal and Joomla.

On October 29, 2026, NHS England Digital updated its advisory to include exploitation developments.

On November 3, 2026, Singapore's Cyber Security Agency also published an alert describing reported active exploitation against affected network and security products.

This demonstrates why organisations should not treat these vulnerabilities as theoretical security problems.

Publicly accessible services running vulnerable PHP versions need immediate attention.

## 5. The Additional PHP Security Concern: CVE-2026-115560

The PHP2Shell vulnerabilities are not the only recent PHP security concern.

A further remote code execution issue, tracked as CVE-2026-115560, was reported in October 2026.

At the time of writing, detailed technical information about this issue remains limited.

CERT-EU has reported that disabling PHP session upload progress can provide protection against the identified attack path until a regular PHP bugfix release becomes available.

Temporary mitigation:

```
session.upload_progress.enabled=0
```

The setting must take effect before request parsing, and PHP workers must be restarted.

Do not assume that this setting is a universal mitigation for PHP2Shell. It is guidance for the separately reported CVE-2026-115560 issue.

Organisations should follow the latest official PHP security advisory for further updates.

## 6. Another Related Issue: The Brotli Decoder Vulnerability

There is also a separate vulnerability worth monitoring.

CVE-2026-111497 affects Google's Brotli compression library and involves an out-of-bounds write during decompression.

Brotli is used by several software ecosystems, including certain PHP Windows builds.

This is not one of the two PHP2Shell runtime vulnerabilities. However, it demonstrates how a vulnerability in a shared dependency can affect multiple products and platforms.

Organisations should identify whether their software bundles an affected Brotli version and follow the relevant vendor security updates.

## 7. What Should Businesses Do Immediately?

If your business operates a PHP-based website, SaaS platform, customer portal or API, the following actions should be prioritised.

### Step 1: Identify Your PHP Version

Check the PHP version running in your production environment.

```
php -v
```

For PHP-FPM deployments, verify the actual FPM version and configuration rather than relying only on the CLI version.

A server can have multiple PHP installations, and the CLI version may differ from the version serving website traffic.

### Step 2: Upgrade to a Fixed PHP Release

Move to an updated, supported PHP release.

The fixed versions for the PHP2Shell vulnerabilities are:

* PHP 8.5.12
* PHP 8.4.27
* PHP 8.3.36
* PHP 8.2.35

Use the latest supported vendor-provided security package available for your environment.

If you are running an end-of-life PHP branch, plan a migration to a supported version.

### Step 3: Restart PHP Workers

Installing a package does not always mean existing worker processes have started using the updated runtime.

For PHP-FPM systems, restart the relevant service after updating.

For example:

```
sudo systemctl restart php8.4-fpm
```

Replace the service name with the actual PHP-FPM version installed on your server.

Restart the relevant web server or application process where required.

### Step 4: Review Server Logs

Review relevant web server, PHP-FPM and application logs for unusual activity.

Look for:

* Unexpected HTTP 500 errors.
* Unusual request patterns.
* Unexpected PHP worker restarts.
* Abnormal resource consumption.
* Unexpected child processes.
* Suspicious outbound connections.
* Unusual file modifications.

Do not assume that an absence of obvious log entries proves that your system has not been compromised.

### Step 5: Investigate Potential Compromise

If your environment was exposed while running a vulnerable version, patching alone may not be sufficient.

Investigate suspicious activity, review privileged accounts, inspect unexpected processes and files, and assess whether credentials or secrets could have been exposed.

If compromise is suspected, isolate the affected system where appropriate and follow your incident response procedures.

Rotate potentially exposed credentials and secrets after determining the scope of the incident.

### Step 6: Review Your Application's Security

A secure PHP runtime does not automatically make a web application secure.

Businesses should also review:

* Authentication and session management.
* API access controls.
* SQL injection exposure.
* Cross-site scripting.
* File upload handling.
* Insecure direct object references.
* Server configuration.
* Access permissions.
* Third-party dependencies.

Security should be evaluated across both the application and the infrastructure supporting it.

## 8. Why Startups and SaaS Businesses Should Pay Attention

For startups, security incidents are not just technical problems.

A compromised production server can create financial, operational and reputational consequences.

Consider a SaaS company that processes customer information, handles subscriptions and stores business-critical data.

If an attacker gains remote code execution on its PHP server, the potential impact may extend beyond the website itself.

Depending on the server's privileges and network access, attackers could potentially:

* Access application configuration and secrets.
* Attempt to extract database credentials.
* Read sensitive files.
* Manipulate application processes.
* Establish persistence.
* Move towards other accessible infrastructure.

The actual impact depends on the environment, permissions, network segmentation and security controls.

A small development team may not have a dedicated security engineer continuously monitoring these risks.

That is precisely why regular vulnerability assessments, dependency reviews and infrastructure security checks matter.

**Security should not become a priority only after customers start reporting problems.**

## 9. The Bigger Lesson: Application Security Is More Than Writing Secure Code

PHP2Shell highlights an important reality.

A development team can follow secure coding practices, implement authentication, validate inputs and use HTTPS, yet still operate an application on top of a vulnerable runtime.

Application security is not limited to the code written by developers.

It includes:

* Programming language runtimes.
* Third-party libraries.
* Frameworks and dependencies.
* Web server configurations.
* Cloud infrastructure.
* Authentication and authorization.
* API security.
* Deployment and update processes.

Organisations need a continuous approach to identifying and managing vulnerabilities across their technology stack.

A single security assessment cannot replace ongoing patch management, monitoring and secure development practices.
